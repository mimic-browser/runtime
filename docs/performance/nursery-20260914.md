# V8 young-generation limit, 2026-09-14

Keep the existing 4 MiB maximum young generation. An 8 MiB limit improves the
CPU workload by about 12%, but leaves DOM execution essentially unchanged and
increases its memory cost. A 16 MiB limit also reduces DOM throughput. None of
the alternatives meets the campaign's requirement for at least twice the speed
when accepting greater Page memory. This bounded experiment stops global
nursery retuning; it does not introduce adaptive settings or workload heuristics.

## Experiment

The four production CLI binaries differ only in the two calls to
`SetMaxYoungGenerationSizeInBytes` in `internal/engine/v8/spike.go`, covering
ordinary and snapshot-restored isolates: 2, 4, 8 or 16 MiB. The same native V8
library, ABI, pinned `--no-extensible-ro-snapshot` behavior, Page isolation,
bootstrap, wrappers and tracing remain in use. A maximum is a resource
constraint, not a promise that every Page allocates that amount.

The source base is an immutable capture of the optimized production changes
over f07bd2d, including the DOM, value-lifetime, binary Fetch, shared bootstrap
bytes and memory-only response-body sharing improvements. Forty-nine captured
source files and each variant's exact source and binary hashes are recorded in
the receipt. The earlier CSS and prebuilt-bootstrap prototypes are excluded.
Subsequent unrelated module-error lifetime corrections are outside this capture.

All processes, workload servers and the CDP controller run on Linux. Two
sequential series use order 4/2/8/16 and 16/8/2/4, with no concurrent heavy builds or
tests. Every process executes CPU then DOM. Each workload has one excluded warmup
and three measured single-Page operations, followed by one wave of ten Pages
held alive until every workload completes. Resources are fully loaded, HTTP
cache is disabled, each Page has a separate origin, and the frozen fixtures and
correctness checks are unchanged. All 224 Page operations pass: 64 single-Page
operations including warmups and 160 operations in sixteen held-Page waves.
All eight processes exit successfully, with no swap input during the waves.

## Results

Single-Page medians of six measured operations per setting/workload, milliseconds.
Whole operation includes session creation, workload completion and teardown;
execution is the unchanged harness execution interval.

| Maximum young generation | CPU execution | CPU whole operation | DOM execution | DOM whole operation |
| --- | ---: | ---: | ---: | ---: |
| 2 MiB | 42.034 | 78.900 | 104.838 | 138.340 |
| 4 MiB, current | 35.212 | 73.365 | 108.895 | 148.394 |
| 8 MiB | 31.368 | 65.398 | 108.154 | 145.632 |
| 16 MiB | 32.130 | 68.767 | 113.866 | 148.777 |

Ten-Page waves, medians of two waves per setting/workload. Throughput includes
creation, completion and teardown. CPU is process CPU consumed by the wave,
not an independently additive cost on top of wall time.

| Maximum young generation | CPU Pages/s | CPU seconds/wave | DOM Pages/s | DOM seconds/wave |
| --- | ---: | ---: | ---: | ---: |
| 2 MiB | 47.287 | 1.755 | 27.670 | 3.485 |
| 4 MiB, current | 43.434 | 1.460 | 26.437 | 3.720 |
| 8 MiB | 52.335 | 1.135 | 25.179 | 3.905 |
| 16 MiB | 49.247 | 1.225 | 23.667 | 4.375 |

Memory is Linux USS, MiB per Page. Marginal means `(held - process ready) / 10`;
incremental means `(held - warm before wave) / 10`. CPU precedes DOM in the same
process, so its allocator history can affect the latter. Both baselines are
retained to make that distinction visible.

| Maximum young generation | CPU marginal | CPU incremental | DOM marginal | DOM incremental |
| --- | ---: | ---: | ---: | ---: |
| 2 MiB | 53.492 | 37.959 | 69.485 | 40.364 |
| 4 MiB, current | 55.251 | 38.293 | 73.992 | 44.144 |
| 8 MiB | 51.650 | 36.506 | 75.976 | 48.231 |
| 16 MiB | 58.516 | 41.931 | 83.353 | 55.065 |

At 8 MiB, CPU execution and whole-operation speedups are both 1.12x; CPU wave
throughput improves 20.5% and wave CPU falls 22.3%. DOM execution improves only
0.7%, wave throughput falls 4.8%, and marginal/incremental memory rises
2.7%/9.3%. The CPU improvement therefore does not establish a general setting
that satisfies the selected tradeoff. At 16 MiB, DOM throughput falls 10.5%,
wave CPU rises 17.6%, and marginal/incremental memory rises 12.7%/24.7%.
At 2 MiB, lower DOM memory accompanies a 19.4% CPU execution regression and
20.2% greater CPU consumption per wave.

Post-close memory is retained in the evidence without forced Go or V8 GC. After
the DOM wave and 250 ms recovery, whole-process USS is approximately
469/497/477/481 MiB for 2/4/8/16 MiB respectively, down from held values
716/762/781/855 MiB. These short recovery samples include allocator capacity and
cannot establish recovered live heap, a leak, or long-session retention.

Process-to-first-CPU-result medians are 510/535/426/447 ms for 2/4/8/16 MiB.
There are only two cold processes per setting, and even pre-Page CDP readiness
varies from 72 to 128 ms across setting medians. These startup observations are
archived, but do not establish a repeatable startup improvement from nursery
size. The single-Page table excludes each workload's first operation.

## Decision and limits

This is a screening experiment, with two held-Page waves per workload and no
long-session or 100-Page matrix. The results do not prove a universal optimum at
4 MiB; they reject expanding this global tuning direction under the campaign's
speed/memory criteria. No candidate needs production integration or promotion
tests. An adaptive policy would require separate architectural evidence and is
outside this experiment.

Chrome is not rerun for each limit. All four variants use the same frozen CPU
and DOM assertions. The preceding [V8 environment experiment](v8-environment-20260914.md)
already shows that most of the pure CPU gap to Chrome exists inside minimal
Mimic V8. The modest nursery benefit leaves native build/JIT/GC differences
unresolved; it does not justify claiming that GC alone explains the gap.

[data/nursery-20260914](data/nursery-20260914/) contains compressed complete raw
rows, medians and relative changes, source/binary/harness hashes, and the exact
experiment policy. To repeat the bounded slice, build those four resource
constraint values against one identical production source snapshot, execute the
unmodified CPU/DOM fixtures through the Linux CDP adapter with the order and
sampling above, and hold ten independent Pages per wave before teardown.
Temporary variant sources, overlays, runner and binaries are discarded after
the campaign; the evidence and reproduction contract remain.
